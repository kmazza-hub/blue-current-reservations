# V100.3.116 — Managed backup and release protection

The hosted pilot now maintains dated, checksum-verified recovery points through
its existing persistence queue. The hosted image enables a six-hour interval,
28-point retention, immediate startup protection when needed, and five-minute
retry polling. Shutdown waits for an in-flight snapshot. Backup failures are
logged without exposing content or stopping restaurant service. Backups remain
on the existing persistent disk; this is not independent off-disk disaster
recovery. No automatic restore, database reset, new public endpoint, or restaurant
activation is introduced. Non-hosted development remains opt-in.

Two historical demo runtime snapshots (including obsolete session state) are
removed from the current tree, with Git history preserved. Recursive Git/Docker
exclusions prevent nested runtime databases, backups, local authority files, and
secrets from entering new releases. A recursive release-data check runs both in
certification and inside the Docker build after COPY.

GitHub Actions runs the current release certification and builds the hosted image
on live-service-timeline/main pushes and pull requests, with read-only repository
permissions. Render auto-deploy remains off. Historical exact-version/source-text
test snapshots remain preserved. Three tests still used by current certification
now accept forward V100.3 releases rather than a fixed version allowlist, retaining
their contrast, asset, isolation, and host-workspace behavior assertions.
The current certification command is the active
release contract and includes behavioral authentication, tenant isolation,
reservation lifecycle, failure/rush, restart, and backup recovery checks.

Wharfside/Frank presentation and both main-page return links remain intact.
Restaurant booking activation remains HOLD pending approved venue configuration,
physical acceptance, backup/recovery acceptance, and authorized manager approval.

Validation: run `npm run certify:universal` and verify the actual GitHub run,
Render health/version, protected recovery metadata, and fictional demo lifecycle
after deployment. A successful local run is not physical device acceptance.
