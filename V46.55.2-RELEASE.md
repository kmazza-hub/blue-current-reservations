# BLUE CURRENT V46.55.2 — LOCAL STABILITY HOTFIX

## What was actually wrong

The latest V46.55.1 repository is structurally valid:
- all referenced client script files exist
- all 326 sampled startup registrations resolve to creator functions
- undefined exported `*Module` variables: 0
- all executive API routes shown in the browser screenshot exist on the server

The browser screenshots exposed two separate stability issues.

### 1. Unhandled transient fetch failure
`executiveWorkflowComposerCenter` started an async load without a catch boundary.

When Edge reported `ERR_NETWORK_CHANGED`, that one module surfaced:

`Uncaught (in promise) TypeError: Failed to fetch`

The endpoint itself exists; the problem was client error handling during a temporary network-stack change.

### 2. OneDrive database file locking
The runtime database path is under OneDrive.

Windows/OneDrive can temporarily lock a JSON file during rename, producing:

`EPERM`

The database service already had a safe copy fallback, but it first retried atomic rename up to seven times. On a known cloud-synced path this created avoidable delay and warning noise.

## V46.55.2 changes

### Network resilience
- Guards Executive Workflow Composer startup fetches.
- Retries Executive Workflow Composer when the browser returns online.
- Guards Executive Command Center startup/refresh fetches.
- Retries Executive Command Center when connectivity returns.
- Guards Kitchen Command Center startup fetches.

### Cloud-synced database stability
Adds cloud-sync path detection for:
- OneDrive
- Dropbox
- Google Drive

On those paths, atomic rename is attempted once. A transient Windows lock then moves immediately to the existing safe backup/copy fallback instead of burning through the full seven-rename retry cycle.

Normal non-cloud paths retain the existing retry behavior.

## What V46.55.2 does not claim to fix

`ERR_NETWORK_CHANGED` is emitted by Chromium/Edge when Windows reports a network-interface change. That event is outside Blue Current.

Blue Current can, however, avoid turning a brief network transition into unhandled application errors and can recover cleanly once localhost is reachable again. That is what this hotfix does.
