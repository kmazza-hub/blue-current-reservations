# V72.0.0 — Managed Database Adapter Contract & Shadow-Store Execution Layer

V72 advances the managed-database migration path while keeping the current JSON persistence authoritative.

## Managed adapter contract

A future managed relational adapter must provide:
- read/list/get/create/update
- transaction
- health
- schema version
- migration application

and must certify:
- transactions
- atomic multi-collection mutation
- durable writes
- concurrent multi-node writers
- row-level locking
- database constraints
- managed failover

Incomplete adapters fail closed.

## Deterministic backfill execution

V72 creates deterministic replay-safe migration batches with:
- store
- batch ordinal
- offset/count
- SHA-256
- stable batch ID

The backfill target can safely receive the same batch again without duplicating imported records.

Admin:
`GET /api/system/persistence-backfill-plan`

## Shadow execution

V72 adds an isolated non-authoritative migration shadow store.

Admin:
`GET /api/system/persistence-shadow`
`POST /api/system/persistence-shadow/seed`

Seeding:
1. resets the migration shadow store
2. executes deterministic backfill
3. enables shadow-read mode
4. compares every source/target store
5. reports mismatches

The shadow store is process-local migration infrastructure and is never the production authority.

## Guarded replication semantics

The replication coordinator defines:
`authoritative commit -> shadow mirror -> mismatch/reconciliation signal`

V72 explicitly does NOT claim a distributed transaction. If a future dual-write target fails after the authoritative write, the operation requires reconciliation rather than pretending both stores committed atomically.

Normal restaurant business writes are not attached to shadow replication in this wave.

## Safety

- JSON remains authoritative
- shadow mode defaults disabled
- no external managed DB connection
- no automatic dual-write
- no automatic failover
- no automatic cutover
- rollback remains available
