# V70.0.0 — Production Configuration, Secrets Integrity & Deployment Readiness

V70 turns production startup into an explicit readiness decision instead of relying on development defaults.

## Fail-closed production configuration

`BLUE_CURRENT_ENV=production` now requires:
- explicit `BLUE_CURRENT_ALLOWED_ORIGINS`
- HTTPS browser origins only
- no wildcard origins
- a database path outside known desktop cloud-sync folders
- valid request/session/security policy ranges
- no plaintext user passwords
- no obvious plaintext API keys/tokens/secrets in persisted state
- environment-backed secrets for configured live connectors

Configuration reports never expose secret values.

## Deployment topology truth

The current persistence layer is explicitly identified as:

`single-node-durable-json`

It has verified recovery, backup integrity, restart reconciliation, and durable writes, but V70 does **not** claim it is safe for concurrent multi-node writers. That constraint is surfaced in deployment readiness instead of being hidden.

## Production startup gates

The HTTP listener will not open in production when:
- configuration readiness has errors
- no verified recovery backup exists
- unfinished mutation recovery contains `reconcile-required` operations

Development remains convenient and continues to support localhost / temporary Cloudflare tunnels.

## Production CORS change

In production, browser origins are explicit-only. `localhost` and `*.trycloudflare.com` are no longer implicitly trusted when `BLUE_CURRENT_ENV=production`.

## Graceful shutdown

SIGINT/SIGTERM now:
1. stop accepting new connections;
2. drain the persistence queue;
3. create a final verified recovery checkpoint;
4. exit only after shutdown finalization.

## Diagnostics

Admin-only:

`GET /api/system/deployment-readiness`

## Deployment configuration template

V70 adds `.env.example` and expands `.gitignore` to exclude environment files, private keys, and database recovery artifacts.
