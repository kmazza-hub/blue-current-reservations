# V68.50.0 — Database Recovery, Backup Verification & Restart Integrity

V68.50 hardens the Blue Current persistence layer for real restart and file-corruption failure modes.

## Verified rolling backups

The JSON database now maintains:
- `<database>.bak`
- `<database>.bak.meta.json`
- `<database>.bak.prev`
- `<database>.bak.prev.meta.json`

Backup manifests contain SHA-256, byte length, source, and creation time. A backup with a checksum mismatch is rejected even if its JSON still parses.

## Automatic startup recovery

The server forces a database read before opening the HTTP listener.

If the primary database is missing or invalid:
1. the newest backup is checksum-verified;
2. if invalid, the previous verified backup is tried;
3. the corrupt primary is preserved as a forensic `.corrupt.<timestamp>.json` copy;
4. verified backup data is durably staged and restored;
5. startup continues only if a readable database exists.

The system does not fabricate an empty database when recovery is unavailable.

## Restart mutation reconciliation

V68 prepared-mutation journal entries are now reconciled on restart.

- durable completion evidence -> `committed-recovered`
- durable failure evidence -> `failed-recovered`
- no proof either way -> `reconcile-required`

Ambiguous operations are never silently retried.

## Diagnostics

`GET /api/system/database-recovery`

returns:
- database recovery statistics
- newest/previous backup verification state
- latest recovery source
- mutation-integrity health
- reconcile-required count

## Startup

The listener opens only after:
- primary read / verified recovery
- startup backup checkpoint
- unfinished-mutation reconciliation
- authentication password initialization
- backup verification
